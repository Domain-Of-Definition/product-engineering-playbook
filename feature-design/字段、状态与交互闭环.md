# 后台业务功能中的字段、状态与交互闭环设计

## 背景

后台管理系统中的很多返工，并不是因为某个页面“不会写”，而是因为一个字段或状态只在某一个环节被考虑，而没有贯穿整个功能生命周期。

因此，在实现功能之前，需要先完成字段、状态和交互规则的闭环设计。

# 一、字段必须形成完整生命周期

一个业务字段通常不会只存在于数据库或者表单中。

设计字段时，应同时检查它是否涉及：

- 数据库存储
- 列表展示
- 查询条件
- 新增表单
- 修改回填
- 批量导入模板
- 导入解析
- 后端请求参数
- 后端查询
- 后端保存
- 变更记录
- 数据导出

如果一个字段发生：

- 新增
- 删除
- 重命名
- 类型调整
- 规则调整

就需要重新检查整个字段链路，而不能只修改前端页面。

## 字段定义本身也需要完整

每个字段至少需要明确：

- 是否必填
- 是否允许修改
- 哪些角色可以查看
- 哪些角色可以操作
- 数据来自用户输入、系统生成还是关联数据
- 是否支持查询
- 是否需要模糊查询
- 是否包含敏感数据
- 数据格式
- 合法取值范围
- 是否影响其他状态或业务关系

我把这种设计方式理解为：

> **字段生命周期闭环。**

字段不是表单中的一个输入框，而是贯穿 UI、API、数据库、权限和业务规则的一项完整业务定义。

# 二、状态必须在编码之前设计

另一个容易造成返工的问题是：

> 一边开发功能，一边临时增加状态。

对于存在生命周期的业务对象，编码前至少应该明确：

- 有哪些状态
- 状态之间如何转换
- 哪些角色允许执行状态转换
- 每个状态允许哪些操作
- 每个状态显示哪些按钮
- 状态变化会影响哪些关联数据

例如在房屋业务中，可以存在：

- 未售出
- 已售出未绑定
- 已绑定

只有进入“已绑定”状态后，某些业主关联信息才具有明确业务意义。

如果解除绑定，则不仅是修改页面上的一个状态，还可能需要同步结束对应的人房关系。

因此：

> 状态变化往往不仅是字段值变化，而是业务规则的触发点。

对于工单等更加复杂的业务对象，更应该先明确状态流转，再决定每个状态可以执行哪些操作。

# 三、批量导入应该从用户视角设计

后台系统经常需要支持 Excel 批量导入。

导入设计不能直接把数据库内部结构暴露给用户。

例如用户更容易理解：

- 小区名称
- 省、市、区
- 幢号
- 单元号
- 房号
- 人员姓名
- 手机号

而不应该要求用户理解数据库中的内部 ID。

内部编号和关联关系应该由系统负责匹配。

## 导入结果必须足够明确

用户完成导入以后，系统应该明确返回：

- 成功多少条
- 失败多少条
- 重复多少条
- 哪一行失败
- 哪个字段错误
- 具体失败原因

对于重复数据，应优先避免再次写入。

这样用户修正错误数据后重新上传时，之前已经成功的数据不会被重复创建。

# 四、页面交互应该保持一致

在同一类后台系统中，页面行为最好保持统一。

我在实践中逐渐形成了以下规则：

- 新增、修改、删除等操作尽量在当前业务页面完成。
- 修改数据时，应完整回填现有数据。
- 查询默认展示当前用户有权限访问的数据。
- 筛选条件应根据业务需要决定是否必填。
- 文本型业务筛选可以根据场景支持包含式模糊查询。
- 表格序号与实际业务数据主键解耦。
- 编号列和操作列可以固定，业务字段根据内容调整展示空间。
- 页面只展示用户真正需要看到的业务字段。
- 导入需要的字段不等于列表中必须展示的字段。
- 外部 Demo 可以作为交互或视觉参考，但不能替代真实业务结构设计。

## 可复用原则

### 字段设计不是 UI 设计

一个字段意味着一整条数据生命周期。

### 状态设计应该先于按钮设计

按钮是否存在，应该由状态和权限共同决定，而不是开发过程中临时增加。

### 用户不应该理解数据库

导入、查询和编辑界面应该使用业务语言，系统内部负责完成 ID、关联和数据结构转换。

### 同类页面应该共享交互规则

一致性本身就是降低系统复杂度的一种方式。
