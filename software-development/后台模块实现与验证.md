# 后台业务模块的实现、事务与测试闭环

## 背景

一个后台功能在页面上“看起来可以使用”，并不代表它已经真正完成。

完整实现需要同时验证：

- 前端
- API
- 后端业务逻辑
- 数据库
- 权限
- 真实运行环境

因此，我逐渐形成了一套从接口设计到最终验证的实现方法。

# 一、按照业务能力设计接口

根据具体页面需要，一个业务模块通常需要考虑：

- 列表查询
- 详情查询
- 新增
- 修改
- 启用 / 禁用
- 删除 / 恢复
- 导入
- 导出
- 关系绑定 / 解绑
- 变更记录查询

并不是每个页面必须拥有所有接口，而应该根据真实业务能力进行选择。

# 二、所有后端写操作都要考虑完整性

后端写操作需要统一考虑：

- 独立鉴权
- 数据范围校验
- 事务
- 防止重复提交
- 幂等
- 数据去重
- 业务规则校验
- 关联数据校验
- 同步写入变更记录
- 返回清晰的错误字段和失败原因

对于同时修改多项关联数据的业务操作，应避免只成功一部分。

# 三、批量导入需要多层校验

批量导入可以拆成三层。

## 第一层：模板约束

通过 Excel 模板提前降低错误概率，例如：

- 下拉选项
- 日期格式
- 填写说明

## 第二层：上传后的基础校验

检查：

- 必填项
- 枚举值
- 格式
- 组合字段

## 第三层：后端业务校验

最终仍然需要检查：

- 当前用户权限
- 数据访问范围
- 重复数据
- 关联数据是否存在
- 业务规则是否合法

前端校验用于改善用户体验，后端校验负责保证业务正确性。

# 四、测试不能只验证页面

功能完成以后，至少应该验证四个层面。

### 1. 页面

用户操作是否符合预期。

### 2. 网络请求

请求参数和响应数据是否正确。

### 3. 数据库

数据是否真的按照预期写入、更新或删除。

### 4. 持久化结果

退出页面、刷新浏览器甚至重新登录之后，结果是否仍然正确。

## 五、从单点验证升级为业务闭环验证

随着系统从单个后台页面逐渐扩展到多个角色和多个客户端，我进一步发现：

> 一个页面操作正常、一个接口返回成功，并不能证明对应的业务已经真正完成。

原本的验证方式主要关注：

```text
页面操作
   ↓
请求参数与响应
   ↓
数据库结果
   ↓
刷新 / 重新登录后的持久化结果
```

这套方式对于单个模块仍然有效，但对于会影响：

- 多个业务对象
- 多个角色
- 多个客户端
- 状态事件
- 外部系统

的功能，还需要继续向后验证。

### 业务操作需要继续验证最终事实

例如一个接口返回成功之后，还应该根据业务重要程度继续检查：

1. 权威业务数据是否发生了正确变化。
2. 关联对象是否同步更新。
3. 是否产生了预期的状态事件或审计记录。
4. 当前角色是否只能访问允许的数据范围。
5. 其他相关客户端是否能够读取到一致的结果。

因此，完整的验证链路可以进一步扩展为：

```text
页面行为
   ↓
真实业务接口
   ↓
数据库业务状态
   ↓
业务事件 / 审计记录
   ↓
角色与数据范围
   ↓
其他相关客户端
```

这里需要特别区分两类证据：

### 当前状态

数据库可以回答：

> 现在的业务事实是什么？

例如某个对象当前处于什么状态、关联关系是什么。

### 变化过程

业务事件和审计记录可以进一步回答：

> 它是如何变成现在这样的？

对于涉及：

- 资金
- 权限
- 审批
- 状态流转
- 多角色协作

的关键业务，仅验证最终字段值往往是不够的，还应该确认变化过程符合业务规则。

---

### 外部依赖必须单独验证

对于依赖第三方平台的功能，还需要明确区分：

```text
本地业务逻辑完成
        ↓
接口适配完成
        ↓
等待外部联调
        ↓
真实外部结果验证
        ↓
正式环境验证
```

例如支付、消息、AI、物联或外部存证等能力，即使：

- 页面已经完成
- 后端逻辑已经存在
- Mock 流程能够跑通

也不能因此直接认为外部能力已经真正可用。

因此：

> 模拟成功可以用于验证产品流程，但不能作为真实外部能力的完成证据。

---

### 多端系统要验证的是同一个业务事实

跨端验证的重点也不是：

> 几个页面是不是都能正常打开。

而是：

```text
客户端 A 执行业务操作
        ↓
权威业务数据发生变化
        ↓
客户端 B / C 读取到相同的业务事实
```

不同客户端可以拥有不同：

- 页面形态
- 可见字段
- 操作权限

但不应该各自维护一套互相独立的业务状态。

因此：

> **跨端一致性的核心是共享业务事实，而不是共享页面实现。**

---

### 验证结论也需要有边界

内部开发环境中的业务闭环可以证明：

> 当前功能在已知环境和已知数据条件下能够完成指定流程。

但这并不自动等于：

- 完整集成测试
- UAT
- 客户验收
- 正式上线
- 生产稳定

因此，测试结论本身也应该明确当前验证阶段和仍未覆盖的范围。

更详细的跨端验证、功能分层和可重复测试方法，单独整理在：[跨端业务闭环与分层验收](./跨端业务闭环与分层验收.md) 中。

# 六、必须覆盖不同权限场景

测试数据应该覆盖不同类型的业务角色，例如：

- 高级管理员
- 项目管理员
- 普通管理人员
- 一线业务人员
- 多项目、多身份用户

不能只使用最高权限账号验证功能。

否则很容易遗漏：

- 页面权限
- 操作权限
- 数据范围
- 跨项目数据隔离

等问题。

# 七、验证真实运行环境

有时代码本身已经修改正确，但运行结果仍然不符合预期。

这时还需要检查：

- 当前运行服务是否使用最新代码
- 后端服务是否需要重新启动
- 前端是否仍然使用旧缓存
- 是否仍在加载旧模板
- 数据库迁移是否已经执行
- 下载地址是否已经切换到新版资源

因此：

> 功能验证的对象不是“代码文件”，而是最终真实运行的系统。

# 八、后台模块的标准开发顺序

基于这些实践，我逐渐形成了下面的开发流程：

1. 明确模块包含多少页面。
2. 明确每个页面包含哪些功能。
3. 整理字段以及字段在列表、表单、导入和数据库中的位置。
4. 明确角色权限和数据范围。
5. 明确状态以及状态流转规则。
6. 设计主体数据、关系数据和软删除机制。
7. 设计接口、事务、校验和变更记录。
8. 明确页面交互和异常提示。
9. 准备不同角色的测试数据和完整业务用例。
10. 再进入编码阶段，并完成前端、后端、数据库和真实运行环境验证。

这套顺序的核心思想是：

> 尽可能在编码之前解决设计问题，而不是通过不断修改代码来发现需求和业务规则。

## 可复用原则

### Coding 不是模块开发的第一步

页面、字段、权限、状态和数据关系都应该先于具体编码得到基本确认。

### 写操作默认考虑事务和审计

只要一次操作涉及多项数据变化，就应该考虑原子性和可追溯性。

### 测试目标是业务闭环

页面能点通只是测试的第一层。

真正完成意味着：

> UI、接口、权限、数据库和真实运行环境的结果保持一致。

### 接口成功不是最终完成依据。

对关键业务应继续核对权威数据、关联对象、业务事件和其他客户端结果。

### 多端验证围绕同一个业务事实进行。

不同客户端可以有不同交互，但应该读取和操作同一套权威业务状态。

### 测试结论必须标注验证边界。

Mock、内部闭环、外部联调、UAT 和生产运行属于不同阶段，不能相互替代。
