# 后台业务模块的实现、事务与测试闭环

## 背景

一个后台功能在页面上“看起来可以使用”，并不代表它已经真正完成。

完整实现需要同时验证：

- 前端
- API
- 后端业务逻辑
- 数据库
- 权限
- 真实运行环境

因此，我逐渐形成了一套从接口设计到最终验证的实现方法。

# 一、按照业务能力设计接口

根据具体页面需要，一个业务模块通常需要考虑：

- 列表查询
- 详情查询
- 新增
- 修改
- 启用 / 禁用
- 删除 / 恢复
- 导入
- 导出
- 关系绑定 / 解绑
- 变更记录查询

并不是每个页面必须拥有所有接口，而应该根据真实业务能力进行选择。

# 二、所有后端写操作都要考虑完整性

后端写操作需要统一考虑：

- 独立鉴权
- 数据范围校验
- 事务
- 防止重复提交
- 幂等
- 数据去重
- 业务规则校验
- 关联数据校验
- 同步写入变更记录
- 返回清晰的错误字段和失败原因

对于同时修改多项关联数据的业务操作，应避免只成功一部分。

# 三、批量导入需要多层校验

批量导入可以拆成三层。

## 第一层：模板约束

通过 Excel 模板提前降低错误概率，例如：

- 下拉选项
- 日期格式
- 填写说明

## 第二层：上传后的基础校验

检查：

- 必填项
- 枚举值
- 格式
- 组合字段

## 第三层：后端业务校验

最终仍然需要检查：

- 当前用户权限
- 数据访问范围
- 重复数据
- 关联数据是否存在
- 业务规则是否合法

前端校验用于改善用户体验，后端校验负责保证业务正确性。

# 四、测试不能只验证页面

功能完成以后，至少应该验证四个层面。

### 1. 页面

用户操作是否符合预期。

### 2. 网络请求

请求参数和响应数据是否正确。

### 3. 数据库

数据是否真的按照预期写入、更新或删除。

### 4. 持久化结果

退出页面、刷新浏览器甚至重新登录之后，结果是否仍然正确。

# 五、必须覆盖不同权限场景

测试数据应该覆盖不同类型的业务角色，例如：

- 高级管理员
- 项目管理员
- 普通管理人员
- 一线业务人员
- 多项目、多身份用户

不能只使用最高权限账号验证功能。

否则很容易遗漏：

- 页面权限
- 操作权限
- 数据范围
- 跨项目数据隔离

等问题。

# 六、验证真实运行环境

有时代码本身已经修改正确，但运行结果仍然不符合预期。

这时还需要检查：

- 当前运行服务是否使用最新代码
- 后端服务是否需要重新启动
- 前端是否仍然使用旧缓存
- 是否仍在加载旧模板
- 数据库迁移是否已经执行
- 下载地址是否已经切换到新版资源

因此：

> 功能验证的对象不是“代码文件”，而是最终真实运行的系统。

# 七、后台模块的标准开发顺序

基于这些实践，我逐渐形成了下面的开发流程：

1. 明确模块包含多少页面。
2. 明确每个页面包含哪些功能。
3. 整理字段以及字段在列表、表单、导入和数据库中的位置。
4. 明确角色权限和数据范围。
5. 明确状态以及状态流转规则。
6. 设计主体数据、关系数据和软删除机制。
7. 设计接口、事务、校验和变更记录。
8. 明确页面交互和异常提示。
9. 准备不同角色的测试数据和完整业务用例。
10. 再进入编码阶段，并完成前端、后端、数据库和真实运行环境验证。

这套顺序的核心思想是：

> 尽可能在编码之前解决设计问题，而不是通过不断修改代码来发现需求和业务规则。

## 可复用原则

### Coding 不是模块开发的第一步

页面、字段、权限、状态和数据关系都应该先于具体编码得到基本确认。

### 写操作默认考虑事务和审计

只要一次操作涉及多项数据变化，就应该考虑原子性和可追溯性。

### 测试目标是业务闭环

页面能点通只是测试的第一层。

真正完成意味着：

> UI、接口、权限、数据库和真实运行环境的结果保持一致。
