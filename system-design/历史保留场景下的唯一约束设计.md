# 历史保留场景下的唯一约束设计

## 写在前面

> 特别加入了这一篇，因为这周遇到了好几次“已作废的内容重新新建时遇到重复键的问题”。比如在测试账单作废、资金原路退回后新建同年度账单时，一方面希望作废账单能够保留用于公示，另一方面仍希望新建该年年度账单。这时如果理解为当前记录为全局唯一记录则在新建时会出现重复键的问题。实际上在软删除时要分情况讨论，关键在于**新记录和旧记录，在业务上是不是“同一个对象的连续版本”**：

> **1.同一业务事实的新版本**:旧记录要保留，而且新记录和旧记录存在明确继承关系。例如账单作废后重新生成。这时适合用**版本化**：保留同一个业务根标识，新记录版本号递增。核心是：**不是重新占一个位置，而是在延续同一个业务对象**。

> **2.旧记录已退出当前业务，新记录重新占用这个业务身份**：旧记录只是为了审计、追溯而保留，不再参与当前业务。例如档案删除后重建、文档删除后重新上传。这时适合做仅有效记录唯一：软删除记录不再占用唯一键。核心是：**历史可以重复保留，但当前有效记录只能有一个**。

> 比如账单我们通常会说：“这是原账单作废后的第二版”。但公司档案删除后重建，我们往往只会说：“现在重新建了一条公司档案”。在业务上不需要表达作废公司和新建公司之间是同一个业务对象的版本变迁。

## 背景

在业务系统中，软删除、作废和历史留痕是很常见的设计。

为了保证可追溯性，一条业务记录即使已经失效，通常也不会直接从数据库中物理删除。

例如：

```text
新建
  ↓
使用
  ↓
作废 / 删除
  ↓
保留历史记录
```

这种设计本身没有问题。

但在系统继续运行以后，我逐渐遇到另一类问题：

> 业务已经允许重新建立，数据库唯一约束却仍然认为历史记录占用了这个位置。

典型表现就是：

```text
第一次新建
   ↓
作废 / 软删除
   ↓
重新新建
   ↓
Duplicate Key
```

一开始很容易把这种问题理解成：

> 唯一索引写错了。

但多次遇到类似情况以后，我发现真正需要重新思考的是：

> **数据库中的“唯一”，到底应该约束当前有效业务，还是全部历史记录？**

不同业务对象的答案并不相同。

---

## 一、唯一约束必须和业务生命周期一起设计

设计唯一键时，很容易只考虑：

```text
同一时刻不能出现两条重复数据
```

例如：

```text
组织名称不能重复
文件路径不能重复
某年度账单不能重复
```

但如果业务对象存在：

```text
创建
→ 生效
→ 作废 / 删除
→ 重新建立
```

就必须继续回答一个问题：

> 历史记录失效以后，它是否还应该继续占用这个唯一值？

这取决于业务语义。

因此，唯一约束不能只根据字段设计。

它应该同时考虑：

```text
业务身份
+
生命周期
+
历史保留方式
+
重新建立规则
```

---

## 二、先判断“重新建立”到底意味着什么

遇到历史记录和唯一约束冲突时，我现在会先区分两类业务。

### 1. 同一个业务事实产生了新版本

例如某个周期性业务记录已经作废，但业务上允许重新生成。

这时新的记录并不是：

> 一个与历史完全无关的新对象。

而更像是：

> 同一个业务事实的新版本。

可以理解为：

```text
业务根对象
   ↓
版本 1
   ↓
作废
   ↓
版本 2
   ↓
作废
   ↓
版本 3
```

这种场景中，历史记录本身具有业务意义。

因此不应该简单通过：

```text
删除旧记录
```

或者：

```text
让所有历史记录不参与任何唯一关系
```

解决。

更合理的方式是将：

```text
业务身份
```

和：

```text
业务版本
```

分开。

例如：

```text
业务对象
+
周期
+
版本号
```

共同确定一条具体记录。

重新生成时：

```text
查询已有最大版本
      ↓
新版本 = 最大版本 + 1
      ↓
继续关联同一个业务根对象
```

这样既允许重新生成，又保留了：

```text
版本 1 → 版本 2 → 版本 3
```

之间的历史关系。

---

### 2. 历史记录已经失效，新记录重新占用业务身份

另一类业务中，软删除记录只是为了：

- 审计
- 查询历史
- 恢复问题
- 保留操作痕迹

它已经不再代表当前有效业务。

例如某个档案：

```text
名称 A
状态：有效
```

删除以后：

```text
名称 A
状态：已删除
```

业务上可能允许重新建立新的：

```text
名称 A
状态：有效
```

这时真正需要保证的是：

> 当前不能同时存在两条有效的“名称 A”。

而不是：

> 整个数据库历史上永远只能出现一次“名称 A”。

因此这类场景的唯一性更接近：

```text
当前有效记录唯一
```

而不是：

```text
全部历史记录唯一
```

---

## 三、不要简单把“删除状态”塞进唯一键

一种很自然的设计是：

```text
UNIQUE (
    business_key,
    deleted
)
```

例如：

```text
文件路径 + 删除状态
```

乍看之下似乎可以做到：

```text
有效记录一条
删除记录一条
```

但只要业务允许多次：

```text
新建
→ 删除
→ 重建
→ 再删除
```

问题就会出现。

第一次删除以后已经存在：

```text
路径 A + 已删除
```

重新上传：

```text
路径 A + 有效
```

仍然可以成功。

但第二次删除时又要变成：

```text
路径 A + 已删除
```

于是与第一次删除记录发生唯一键冲突。

也就是说：

> **“业务键 + 是否删除”这种唯一约束，只能容纳一条历史删除记录，并不能真正支持多轮生命周期。**

如果业务要求历史长期保留，这种模型本身就和业务生命周期冲突。

---

## 四、根据业务语义选择“版本化”还是“有效态唯一”

经过几类问题以后，我现在更倾向于先做这样的判断：

```text
历史记录失效后重新建立
          ↓
新的记录是不是旧业务事实的延续？
          ↓
       是 / 否
```

### 如果是同一业务事实的延续

优先考虑：

> **版本化。**

例如：

```text
root_id
+
business_key
+
version
```

历史关系可以表示为：

```text
Root A
 ├─ V1
 ├─ V2
 └─ V3
```

适合：

- 周期性生成记录
- 方案版本
- 发布版本
- 修订后的正式记录

这里要保留的不只是：

> 曾经存在过一条记录。

还要保留：

> 这几条记录之间是什么关系。

---

### 如果只是同一个业务身份被重新使用

优先考虑：

> **仅对当前有效记录进行唯一约束。**

可以理解成：

```text
历史记录
→ 保留
→ 不再参与当前业务唯一性

有效记录
→ 必须满足唯一约束
```

适合：

- 档案
- 配置
- 文件
- 可删除后重新建立的业务实体

这种设计表达的是：

> 数据库可以保存多个历史版本，但任意时刻只能存在一个当前有效对象。

---

## 五、应用层校验和数据库约束解决的是不同问题

很多重复问题会先在应用层增加：

```text
新建前查询是否已经存在
```

这当然有价值，因为它能够给用户更明确的错误提示。

例如：

```text
当前名称已经存在
当前文件已经上传
当前周期已经生成
```

但应用层校验不能替代数据库唯一约束。

因为两个请求可能同时发生：

```text
请求 A：查询 → 不存在

请求 B：查询 → 不存在

请求 A：插入成功

请求 B：继续插入
```

如果没有数据库约束，就可能形成真正的重复业务数据。

因此更完整的设计应该是：

```text
应用层
→ 提前判断
→ 给出业务友好的提示

数据库
→ 最终唯一性兜底
```

也就是：

> **应用校验负责体验，数据库约束负责一致性。**

与此同时，数据库约束本身也必须符合生命周期语义。

否则数据库虽然成功“阻止了重复”，阻止的却可能是业务本来允许发生的合法操作。

---

## 六、跨系统操作还需要考虑“外部成功、本地失败”

这类问题在涉及外部资源时会更加复杂。

例如：

```text
调用外部系统删除资源
        ↓
外部删除成功
        ↓
更新本地软删除状态
        ↓
数据库唯一键冲突
        ↓
本地事务失败
```

最终可能形成：

```text
外部：
资源已经不存在

本地：
仍然显示有效
```

这已经不只是唯一索引问题，而变成：

> **跨系统事实不一致。**

因此涉及外部副作用时，不能简单认为：

```text
本地事务回滚
=
所有事情都恢复原状
```

因为外部系统通常不会跟着本地数据库事务一起回滚。

这时需要记录外部操作结果，并根据事实进行：

- 状态补偿
- 主动查询
- 人工修复
- 重试
- 异常事件留痕

核心原则是：

> **已经发生且无法回滚的外部事实，不能因为本地事务失败就假装没有发生。**

---

## 七、唯一约束调整不能只改索引，还要处理历史数据

当发现唯一约束设计不符合当前生命周期时，修改数据库结构只是第一步。

还需要继续检查：

```text
历史上是否已经产生重复数据？
```

例如因为：

- 重复点击
- 并发请求
- 旧代码缺少校验
- 历史迁移
- 测试数据

可能已经存在多条当前有效记录。

如果直接添加新的唯一约束，数据库迁移本身就可能失败。

因此更稳妥的过程是：

```text
确认新的业务唯一规则
        ↓
检查已有数据
        ↓
识别重复 / 异常记录
        ↓
确定保留与修复规则
        ↓
修复历史数据
        ↓
建立新的数据库约束
        ↓
补充应用层校验
```

数据库迁移本身也应该被视为：

> 一次数据治理过程。

而不仅仅是一条 `ALTER TABLE`。

---

## 八、测试要覆盖完整的生命周期循环

这类问题最容易遗漏的原因之一，是测试只验证：

```text
新建一次
```

和：

```text
删除一次
```

而没有继续验证：

```text
新建
→ 删除
→ 重建
```

甚至：

```text
新建
→ 删除
→ 重建
→ 再删除
→ 再重建
```

因此，对于存在软删除、作废和版本化的业务对象，我现在更倾向于把生命周期循环本身作为测试用例。

至少应该覆盖：

### 单次循环

```text
新建
→ 作废 / 删除
→ 重建
```

### 多次循环

```text
新建
→ 删除
→ 重建
→ 删除
→ 再重建
```

### 并发提交

```text
两个请求同时创建同一个业务身份
```

### 异常恢复

```text
外部操作成功
+
本地状态更新失败
```

### 历史查询

确认重新建立以后：

- 旧记录仍可追溯
- 新记录正常成为当前有效对象
- 历史记录不会参与错误的业务判断

只有这样才能真正验证：

> 数据模型是否支持完整生命周期，而不是只支持第一次操作。

---

## Trade-offs

### 版本化 vs 有效态唯一

版本化能够清楚表达前后业务关系，但会增加：

- 版本管理
- 查询逻辑
- 当前版本判断

仅约束有效记录更简单，但无法天然表达多条历史记录之间的业务继承关系。

选择依据应该是：

> 新记录是不是原业务事实的下一版本。

而不是统一使用同一种软删除方案。

---

### 历史保留 vs 数据模型复杂度

保留历史能够提供：

- 审计
- 追溯
- 恢复依据

但也意味着查询和唯一约束必须显式理解：

```text
当前有效数据
```

与：

```text
历史数据
```

之间的区别。

如果系统没有这种区分，软删除最终往往只是：

> 把物理删除的问题推迟到了后续业务逻辑中。

---

### 应用层去重 vs 数据库去重

应用层能够提供更好的业务反馈。

数据库能够提供并发环境下最终的一致性保证。

二者不是替代关系，而应该共同工作：

```text
应用层提前判断
+
数据库最终兜底
```

---

## 可复用原则

1. **设计唯一约束时必须同时考虑业务生命周期。**
2. **先明确唯一性约束的是当前有效业务，还是全部历史记录。**
3. **重新建立如果属于同一业务事实的延续，应优先考虑版本化。**
4. **历史记录失效后允许重新占用业务身份时，应优先约束有效记录唯一。**
5. **不要简单使用“业务键 + 删除状态”支持可重复软删除，它通常只能容纳一条删除历史。**
6. **产品视角的“允许重建”和数据库层的唯一规则必须保持一致。**
7. **应用层查重负责用户体验，数据库唯一约束负责最终一致性。**
8. **数据库约束调整前必须检查和治理已有历史数据。**
9. **存在外部副作用时，本地事务回滚不能抹掉已经发生的外部事实。**
10. **软删除业务的测试必须覆盖多轮“新建—删除/作废—重建”，而不是只测试一次创建和删除。**
11. **并发提交和异常恢复应该进入唯一性设计的验证范围。**

---

## 总结

重复键问题表面上发生在数据库。

但当它反复出现在：

```text
作废后重建
删除后重传
档案删除后重新建立
```

这些场景中时，真正需要检查的往往不是：

> 唯一索引语法有没有写对。

而是：

> **数据库中的唯一性是否真正表达了业务中的唯一性。**

对于需要长期保留历史的系统，可以进一步把问题拆成：

```text
这是同一业务事实的新版本？
        ↓
      版本化

还是历史对象已经退出当前业务，
新的对象重新占用这个业务身份？
        ↓
   当前有效记录唯一
```

因此，我现在更倾向于认为：

> **软删除不是给记录增加一个删除标记就结束了，它会直接影响唯一性、重新建立、查询、并发和异常恢复的设计。**

真正可靠的唯一约束，应该约束：

> **业务当前真正不能同时存在的事实，而不是机械地限制数据库历史上曾经出现过的值。**
