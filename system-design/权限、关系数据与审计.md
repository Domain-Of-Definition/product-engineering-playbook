# 后台管理系统中的权限、关系数据与审计设计

## 背景

随着后台系统中的角色、业务对象和数据关系逐渐增加，仅仅依赖简单的“菜单权限”很快就会遇到问题。

在基础数据管理模块开发过程中，我逐渐明确了三个需要独立设计的系统能力：

- 权限模型
- 关系数据模型
- 数据生命周期与审计

# 一、功能权限和数据权限必须分开

功能权限解决的是：

> 用户能不能执行这个操作？

例如：

- 能不能新增
- 能不能修改
- 能不能删除
- 能不能导入
- 能不能导出
- 能不能查看敏感信息

数据权限解决的是：

> 用户能够看到和操作哪些数据？

例如在一个多项目业务系统中：

- 高级管理角色可以访问其管理范围内的多个项目。
- 项目级管理人员只能访问已经授权的项目。
- 同一个用户可能在不同项目中拥有不同身份。

因此：

> 拥有某个菜单的访问权限，并不意味着拥有其中所有数据的访问权限。

同样：

> 前端隐藏按钮也不代表系统已经完成权限控制。

后端接口仍然需要独立鉴权。

## 权限设计至少需要覆盖四层

菜单或权限配置应该考虑：

1. 一级模块是否可见。
2. 二级页面是否可见。
3. 页面中的具体操作是否允许。
4. 当前用户可以访问的数据范围。

# 二、关系数据应该与主体档案分开

复杂业务中的关系通常不适合直接塞进主表字段。

例如物业服务场景中可能出现：

- 一个人关联多套房屋。
- 一套房屋关联不同类型的人员。
- 一个人在不同小区拥有不同身份。
- 一辆车辆可以独立建档，再关联人员、房屋和授权期限。

这些场景本质上包含：

- 一对多
- 多对多
- 带属性的关系

因此，更合理的方式是：

> 主体档案负责描述“对象是什么”，关系表负责描述“对象之间是什么关系”。

关系数据本身也可能需要记录：

- 关系类型
- 生效时间
- 失效时间
- 状态
- 数据来源
- 创建信息
- 修改信息

这样可以避免把大量关系逻辑堆积在主体数据表中。

## 展示结构不一定等于存储结构

一个业务对象关联多个对象以后，列表中是否需要重复展示，应根据用户的查询目标决定。

不能因为数据库中一个人只有一条主体档案，就强制要求所有业务列表也只能出现一条记录。

# 三、业务数据优先采用软删除

对于具有业务价值的数据，不应轻易直接进行物理删除。

更适合采用统一的软删除机制，例如记录：

- 删除状态
- 删除人
- 删除时间
- 删除原因
- 对应变更记录

普通业务查询默认过滤已经删除的数据。

只有在清理明确错误的测试数据等受控场景下，才考虑进行物理删除。

如果物理清理涉及多张关联表，则应作为一个完整的数据操作处理。

# 四、变更记录应该成为统一系统能力

以下写操作都可能需要留下变更记录：

- 新增
- 修改
- 启用
- 禁用
- 删除
- 恢复
- 绑定
- 解绑
- 批量导入
- 状态流转
- 管理员人工修正

对于用户展示，可以保留真正有意义的信息：

- 操作类型
- 操作人
- 操作时间
- 修改人
- 修改时间
- 修改原因

底层还可以保存更完整的变更数据用于审计，但不应该直接把原始内部数据结构展示给普通业务用户。

# 五、明确业务数据的权威来源

系统集成时，首先需要确认：

> 哪个系统拥有这项业务事实？

如果某项数据已经由外部系统负责维护，当前系统原则上不应再建立一套可以独立修改的副本。

否则会产生：

- 数据来源不一致
- 双向同步
- 冲突处理
- 数据覆盖
- 对账
- 责任边界不清

等问题。

当前系统可以根据业务需要保存：

- 外部数据引用
- 同步或清洗任务
- 数据质量问题
- 业务加工结果
- 操作和审计事件

但应避免无必要地重新成为该业务事实的所有者。

## 可复用原则

### 功能权限与数据权限是两个维度

“能不能做”和“能对哪些数据做”必须分别设计。

### 主体和关系分离

当业务关系开始具有自己的类型、状态和生命周期时，就应该考虑独立关系模型。

### 删除也是一种业务状态

在需要审计和追溯的系统里，删除往往不应该意味着数据立即消失。

### 所有写操作都应该考虑可追溯性

系统不仅要知道“现在的数据是什么”，还应该在需要时回答：

> 谁在什么时候，通过什么操作，把数据变成了现在这样？
